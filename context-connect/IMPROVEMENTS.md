# Improvements — خطة تحسين صغيرة وقابلة للتحقق

**الحالة: PROPOSED، وليست إصلاحات منفذة.** طلبك الحالي فوّض المراجعة وإضافة المجلد، وليس تعميم القواعد أو تعديل الأمان. كل دفعة تنفيذية لاحقة لها موافقة منفصلة مرتبطة بالنطاق والـbase commit. لو تغيرت المواصفة، تُراجع الموافقة.

## تصميم السياق الذي أنصح به

- **قواعد عامة قصيرة:** حدود النطاق، الأسرار، الموافقة، التحقق. مصدر معتمد واحد والباقي مؤشرات؛ لا تجعل كل ملف يعلن أنه «فوق كل القواعد».
- **سياق مشروع محلي:** هويته، شجرته الفعلية، أوامر الاختبار، الملفات المسموح تعديلها. لا تفترض وجود مكونات من مشروع آخر.
- **حالة آنية واحدة:** مسؤول/كاتب واحد، task id، revision، status، آخر commit تم التحقق منه، نتيجة الفحص، next action، blocker، وقت UTC. المراجع السرية أسماء متغيرات فقط.
- **HANDOFF مختصر:** ما تحقق، ما لم يتحقق، ما لم يُنفّذ، والخطوة التالية. يشتق من الحالة ولا ينافسها كقاعدة بيانات أخرى.
- **تفاصيل عند الحاجة:** الأدلة والتقارير الطويلة والمهارات لا تدخل جميعها في bootstrap.

ده تصميم مقترح لتعديل العقد لاحقًا؛ لا تنشئ دفتر حالة موازيًا للقائم قبل تحديد خطة ترحيل واضحة. كذلك `last_verified_commit` يعني commit سابقًا موجودًا وقت التحقق؛ لا تحاول كتابة hash الـcommit الذي يحتوي الحقل نفسه.

## توزيع الأدوار مع وكيلك

1. **أنت:** اعتماد النطاق والقرارات الحرجة والموافقة على الدمج.
2. **Antigravity:** فحص جهازك الفعلي، إعداد diff واختبارات وأدلة التنفيذ.
3. **المراجع:** يقرأ diff والنتائج ويصدر GO/HOLD؛ لا يدّعي مراجعة مستقلة إذا كان مجرد تغيير شخصية نفس الجلسة.
4. كاتب واحد لكل ملف/دفعة. عند العمل المتوازي: فروع أو worktrees منفصلة ومالك دمج واضح؛ لا يتسابق وكيلان على `ai_state.json` نفسه.

## بروتوكول push-per-chunk المقترح

1. اقرأ `git status` والـHEAD وremote branch؛ لا تتخلص من تغييرات المستخدم.
2. ثبت قائمة الملفات وشروط القبول؛ نفّذ تغييرًا واحدًا قابلًا للمراجعة.
3. اختبر ثم راجع `git diff` وstaged diff للأسرار. أضف **مسارات محددة**، لا `git add .` على بيئة تحمل captures أو مفاتيح.
4. احفظ commit محليًا، ثم `git fetch origin main` وادمج/أعد تأسيس الفرع بعد مراجعة أي تعارض. لا تسقط تعديل remote آليًا.
5. اختبر الحالة الناتجة ثم push لفرع العمل وأنشئ/حدّث PR. دوّن SHA الذي أكد remote وجوده؛ commit محلي ليس backup خارج الساندبوكس.
6. عند فشل المصادقة/الشبكة: لا تقل «تم الرفع». حافظ على commit وبلّغ العائق دون ZIP أو patch ما لم يطلبه المستخدم، وتوقف عن تكرار المحاولة بلا تغيير في سبب الفشل.
7. لا تعمل squash أثناء كل checkpoint لأنه يمحو نقاط تاريخية نشطة. عند تجهيز PR النهائي، اجمع commits الخاصة بالمهمة فقط. إن كان الفرع منشورًا، لا تعد كتابة تاريخه دون تنسيق؛ استخدم `--force-with-lease` فقط عند الحاجة والموافقة، لا force أعمى.

## تمرين الاستئناف المطلوب لاحقًا

- افتح جلسة جديدة دون المحادثة القديمة، واقرأ bootstrap وHANDOFF والحالة.
- يجب أن يستخرج الوكيل: هوية المشروع، الـbase، آخر commit مؤكد محليًا/بعيدًا، النطاق الموافق عليه، آخر اختبار، blocker، والخطوة التالية.
- افتعل انقطاعًا في **مشروع تجريبي فقط** بين commit وpush، ثم بين ملفي حالة؛ يجب اكتشاف الجزء غير المكتمل وعدم الادعاء بنجاحه.
- معيار نجاح مقترح: تحديد البنود السبعة دون تخمين ودون قراءة أرشيف غير مرتبط. سجّل الوقت/الملفات المقروءة فعليًا للمقارنة، لا تعد بنسبة تحسين مسبقة.

## التراجع

- احتفظ بالمراجع قبل كل دفعة. إذا فشلت، أوقف التفعيل واستعد إعداد المشروع التجريبي بعد مراجعة diff.
- بعد نشر دفعة، يُفضل revert للـcommit المحدد بدل reset يمحو عملًا مشتركًا.
- تغيير schema يحتاج نسخة احتياطية واختبار استعادة؛ revert للكود وحده لا يعيد البيانات المحوّلة.
- لا تنقل/تحذف ملفات البيئة الأصلية حتى تثبت المراجع ويعتمد المالك قائمة المسارات المحددة.
