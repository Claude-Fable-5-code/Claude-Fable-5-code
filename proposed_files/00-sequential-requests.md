## 🏛️ المبادئ الستة الذهبية للتطوير التتابعي

### 1️⃣ التحقق خطوة بخطوة ومطابقة الـ HAR بالسطور (Request-by-Request Flow)
* **القاعدة:** يتم بناء وتجربة طلبات الـ API **ريكويست بريكويست بالترتيب المنطقي الفعلي**.
* **قانون الإسناد المرجعي (دستور بولا - القانون 8):** ممنوع تخمين مسارات الـ API أو الهيدرز. يتم استخراج واقتباس كتلة الـ HAR المرجعية نصاً بالسطور لبيان:
  - مسار الطلب (`url`).
  - الترويسات الإلزامية (`headers`) والترتيب الحساس لها.
  - الحمولة المرسلة (`payload`).
  - بنية الاستجابة المتوقعة (`response schema`) ورموز الحالة (`status codes`).
* **معيار المطابقة:** مقارنة الـ Payload والـ Response المرتجع بالملي مع السجل الأصلي في ملف الـ HAR لضمان المطابقة 100%.

### 2️⃣ نظام التسلسل الرقمي الصارم للإصدارات (Strict Versioning Pattern)
يأخذ كل سكريبت أو ملف أتمتة اسماً رمزياً يعكس بدقة ترتيب التطوير وتاريخ التعديل:
* **تنسيق الاسم الأساسي (رقم صحيح دائمًا للبداية):**
  - الصيغة: `[StepNumber]_[ActionName]_[TargetApp].py`
  - مثال: `01_sign_up_fxpro.py` أو `01_request_otp.py`.
* **التعديل والتصحيح الجراحي (الكسر العشري لحفظ التاريخ ومنع الـ Regression):**
  - إذا تم تعديل أو تصحيح نفس الخطوة -> **نزود الإصدار العشري مع الحفاظ التام على الاسم**:
  - مثال: `01.02_sign_up_fxpro.py` ثم `01.03_sign_up_fxpro.py`.
  - الميزة: سهولة التراجع الفوري، ومقارنة التغييرات (Diffing)، وعدم مسح الكود السابق الشغال.
* **الانتقال للخطوة التالية (رقم صحيح جديد بعد نجاح الخطوة الحالية):**
  - عند نجاح الخطوة 01 بنسبة 100% والانتقال للطلب التالي -> **نبدأ برقم صحيح جديد بدون كسر**:
  - مثال: `02_submit_answers_fxpro.py` ثم `03_verify_dashboard.py`.
* **الشغل الحر والتجارب الاستكشافية (Sandbox):**
  - عند إجراء تجارب حرة، إعادة هيكلة شاملة، أو اختبار بروكسيات/باي باس خارج المسار الخطي:
  - الصيغة: `[StepNumber]_sandbox_[Feature]_[TargetApp].py` (مثال: `04_sandbox_captcha_fxpro.py`).

### 3️⃣ التكامل التشفيري والمراسي (دستور بولا - القانون 1 و 3)
* **الحصانة وتثبيت الهاش:** قبل الانتقال من إصدار لآخر (`01_` إلى `01.02_`)، يتم أخذ نسخة مرساة `.anchor` وحساب بصمة SHA-256 (LF lowercase) وتوثيقها في `Root/ANCHORS.md`.
* **المعمل المسبق والبرهان الكمي:** كل طلب API يجب أن يحتوي على فحص ذاتي كمي يحدد بوضوح شرط النجاح (`PASS / FAIL`) بناءً على الاستجابة الفعلية وليس التخمين.

### 4️⃣ تزامن دفاتر الروت المحلي (Local Root Sync) مع النواة الموحدة
* **القاعدة:** كل مشروع فرعي نشط يمتلك مجلد `Root/` محلي متكامل متزامن مع دفاتر النواة الموحدة (§FATAL RULE #SYNC):
  1. `ai_state.json`: البوصلة اللحظية للحالة والـ Tag النشط والخطوة القادمة.
  2. `PROGRESS.md`: سجل التقدم الخطي والمربعات التفاعلية `[x]` لكافة خطوات الـ API.
  3. `tasks.md`: تفاصيل المهام الفرعية والتحقق التقني.
  4. `memory.md`: توثيق الاكتشافات التقنية وتخطي الحمايات والترويسات غير الموثقة.
  5. `keys.txt`: حفظ التوكنات، الكوكيز، والـ Session IDs المستخرجة حياً أثناء التشغيل.
  6. `ANCHORS.md`: سجل المراسي التشفيرية المشفرة بـ SHA-256 لملفات الخطوات.

### 5️⃣ الـ Git Commit الإلزامي الفوري
* **القاعدة الدستورية:** يُمنع منعاً باتاً الانتقال من خطوة إلى أخرى أو البدء في ريكويست جديد قبل إجراء **Git Commit فوري** يؤمن حالة النجاح الحالية ويحميها.
* **تنسيق رسالة الكوميت:**
  ```bash
  git commit -m "🚀 [ProjectName Step-XX.YY] Successfully verified <Action> API request (100% HAR Parity)"
  ```

### 6️⃣ البانرات النيونية الملونة للبداية والنجاح (Terminal CLI Banners)
يجب أن يطبع كل سكريبت يتم تشغيله واجهات بصرية واضحة ومبهجة في التيرمينال لبيان الحالة التشغيلية:
* **بانر البداية (Start Banner):** يوضح بوضوح: `[STARTING] Request <Step> - <Action>...` مع إظهار التوكن والهدف.
* **بانر النجاح (Success Banner):** عند اكتمال الريكويست بنجاح تام، يطبع بانر أخضر نيون بارز: `[SUCCESS 100%] Step <Step> Verified! Status: 200 OK` مع كود الاستجابة والـ Git Commit المولد.
