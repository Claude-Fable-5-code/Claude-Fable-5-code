## 🚀🚀🚀 SEQUENTIAL REQUESTS & VERSIONING SYSTEM (شرط إلزامي صارم)

> **هذا النظام تم اعتماده بالتنسيق مع زيزو كشرط إلزامي صارم في بيئة العمل لتتبع الطلبات ريكويست ريكويست بالترتيب.**
> **الملف المرجعي المفسر بالكامل:** `.agents/workflows/sequential-requests.md`

### 📋 القواعد الذهبية للتطوير التتابعي:

1. **التحقق ريكويست ريكويست بالترتيب (Request-by-Request Flow):**
   * نقوم ببناء طلبات الـ API واحداً تلو الآخر بالترتيب الفعلي.
   * نقارن الـ headers، والـ payload، والـ response بالملي مع ملف الـ HAR لضمان النجاح 100%.

2. **التسلسل الرقمي الصارم للملفات (Strict Versioning Pattern):**
   * تنسيق اسم الملف: يبدأ برقم صحيح دائمًا في أول مرة بدون كسور (مثال: `01_sign_up_fxpro.py` أو `07_sandbox_fxpro_mailtm.py`).
   * الكسور العشرية تستخدم للتعديل أو الإصلاح فقط (عند اللزوم):
     * لو بنعدل أو نصلح في نفس الخطوة -> **نزود الإصدار العشري ونحافظ على الاسم** (مثال: `01.02_sign_up_fxpro.py` أو `07.02_sandbox_fxpro_mailtm.py`).
     * لو ريكويست جديد أو خطوة تالية -> **نزود الخطوة ونبدأ برقم صحيح بدون كسر** (مثال: `02_submit_answers_fxpro.py`).

3. **تزامن مجلد الروت المحلي (Local Root Sync):**
   * كل مشروع فرعي (مثل `F_Fx_Pro_SMS`) يجب أن يمتلك مجلد `Root` محلي خاص به (`F_Fx_Pro_SMS/Root/`).
   * يجب تحديث ملفات التزامن الأربعة (`ai_state.json`, `TASK.md`, `memory.md`, `keys.txt`) محلياً داخل المجلد ده بعد كل خطوة بالتوازي مع الروت الرئيسي.

4. **الـ Git Commit الإلزامي والبانر الملون لكل خطوة:**
   * **ممنوع تماماً** الانتقال لخطوة جديدة دون إجراء `git commit` فوري يأمن ويحمي حالة النجاح.
   * يجب أن يطبع السكربت بانر نيون ملون فخم للبداية ("جاري البدء...") وبانر نيون مبهج للنجاح ("تم النجاح...") في التيرمينال وتدوين الـ commit.

## 🏓 PING-PONG LOOP PROTOCOL — v1.8 جديد

> **بدل سؤال واحد وخلاص — الكوبري بقدر يتناقش مع الفريق لحد ما يوصلوا لقرار**
> **مستوحى من: Microsoft AutoGen Conversational Patterns**

### إمتى تفعّل Ping-Pong?

| الحالة | الإجراء |
|----------|----------|
| الفريق طلب توضيح (جواب فيه سؤال) | اكتب رد في `chat_send.txt` وشغّل الكوبري تاني |
| الفريق أعطى خيارين لازم تختار | اكتب اختيارك وردّ دور ثاني |
| الفريق دي ADR كامل + واضح | عدي = الدورة خلصت — نفّذ |
| خمس محاولات وما جاش قرار | أخبر المستخدم = [BLOCKED] في ai_state |

### الحد الأقصى = 5 جولات

```
[Antigravity] → Brief → [Team]
[Team]        → Question? → [Antigravity]
[Antigravity] → Answer → [Team]
[Team]        → ADR Final → [Antigravity]
[Antigravity] → ينفّذ الكود
```

### قاعدة الأمان

> لو خمس جولات وما في ADR → أخبر المستخدم وانتظر تدخله — **ممنوع تخمين وتنفيذ لو حد الجولات اتكمل**

## 🚨 Vibe Coding Protocol — إلزامي (Micro-Tasking)

1. **التقسيم الإجباري (Chunking):** ممنوع التنفيذ الأعمى أو كتابة الكود دفعة واحدة. يجب تقسيم أي طلب لخطوات منطقية صغيرة جداً.
2. **اختبر قبل ما تتكلم (Test-Before-Talk):** بعد الانتهاء من كل خطوة، يجب تشغيل الكود واختباره. لا تقم بكتابة كود الخطوة التالية إلا بعد نجاح الحالية.
3. **نقاط التوقف (Checkpoints):** اشرح التغيير وانتظر الموافقة قبل الاستمرار في التعديلات الجوهرية.
4. **التعديل الجراحي (Surgical Edits):** لا تعدل ملفات كاملة، ركز على الدالة المطلوبة فقط.
5. **النقد الذاتي:** اسأل نفسك دائماً: هل سيكسر هذا التعديل أي وظيفة أخرى؟ هل هناك حل أبسط؟
